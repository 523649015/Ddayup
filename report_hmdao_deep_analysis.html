一、执行摘要

本报告深度对标 Infinite-Canvas（GitHub 1.2k Stars）和 RHTV 无限画布（RunningHub 原生 AI 智能体平台）两大业界标杆项目，对 HMDao 项目的技术架构进行全面诊断，并提出从"功能对齐"到"系统可靠闭环"的全链路交付方案。

核心结论：HMDao 目前处于"前端交互层完成、后端数据层缺失"的阶段。前端节点 UI 已按参考图实现（打光/多角度/AI 面板），但缺少后端 API 服务、AI 模型接入链路、WebSocket 实时通信、任务队列管理、以及原生智能体系统。需优先补齐四大短板：后端服务层、模型接入层、智能体系统、数据持久化。

3.2 核心能力差距分析

差距一：后端服务层完全缺失（极高优先级）

当前 HMDao 是纯前端静态部署，所有数据存储在 Zustand 内存中。这意味着：

  • 页面刷新后所有画布数据丢失
  • 无法调用任何 AI 模型 API（图片生成、视频生成、音频生成均为前端 UI 占位）
  • 无法实现用户注册/登录/权限管理
  • 无法保存和分享工作流

差距二：AI 模型接入链路未打通（极高优先级）

文本节点的"GVLM 3.1"、图片节点的"Lib Navi Pro"、视频节点的"Kling O3"、音频节点的"Minimax"均为纯文本标签，无任何实际模型调用能力。需要打通：

ComfyUI Server → HTTP API (/prompt) → WebSocket 进度推送 → 结果回传 → 节点状态更新

差距三：实时通信机制缺失（高优先级）

RHTV 和 Infinite-Canvas 均通过 WebSocket 实现生成进度实时推送（如"节点 3/12 执行中..."）。HMDao 目前无任何实时通信能力。

差距四：智能体系统缺失（高优先级）

RHTV 的核心差异化是"画布原生 Agent"，用户通过自然语言即可自动规划工作流。HMDao 当前仅有"加入 Agent"按钮为占位状态。

差距五：无限画布性能瓶颈（中优先级）

React Flow 在 100+ 节点时可能出现性能问题，需要虚拟滚动、异步分片渲染、节点懒加载等优化。

差距六：数据持久化与版本管理（中优先级）

无项目保存/加载/版本历史/撤销重做（Undo/Redo 栈深度有限）能力。

4.3 AI 模型接入层

4.3.1 ComfyUI 集成方案（核心）

参考 Infinite-Canvas 的实现方式，HMDao 需要构建 ComfyUI API 代理层：

  1. 工作流模板存储：将每种节点类型映射到对应的 ComfyUI API JSON 模板
  2. 参数注入：用户在前端输入的提示词、参数 → 动态替换 JSON 模板中的对应字段
  3. 任务提交：HTTP POST /prompt 到 ComfyUI Server
  4. 进度监听：WebSocket 连接 ComfyUI 的 /ws 端点，实时获取执行状态
  5. 结果获取：通过 /history/:prompt_id 或 WebSocket 消息获取生成结果

六、异常容错与稳定性保障

6.1 异常分类与处理策略

画布渲染崩溃React Flow 内部错误Error Boundary 捕获 + 自动降级为简化视图"画布出现问题，已自动恢复"

6.2 稳定性保障机制

6.2.1 前端容错

  • React Error Boundary：每个节点组件包裹 ErrorBoundary，单节点崩溃不影响整个画布
  • 状态隔离：每个节点的状态独立管理，避免级联故障
  • 数据校验：Zod Schema 校验所有 API 返回数据，防止脏数据污染状态
  • 本地持久化：Zustand persist 中间件自动备份到 localStorage

6.2.2 后端容错

  • 健康检查：/health 端点监控 ComfyUI 连接状态
  • 熔断器：ComfyUI 连续失败 5 次后自动熔断，30 秒后恢复
  • 限流：express-rate-limit 限制单 IP 每分钟 60 次请求
  • 日志：Winston 结构化日志 + 错误追踪（Sentry 集成）
  • 监控：Prometheus + Grafana 监控 GPU 利用率、队列深度、API 延迟

6.2.3 模型调用容错

  • 多模型降级：主模型失败时自动切换到备用模型（如 Kling → HunyuanVideo）
  • 任务队列持久化：BullMQ + Redis，确保任务不丢失
  • 超时控制：图片生成 60s、视频生成 300s、音频生成 30s
  • 资源释放：任务完成/失败后自动清理 GPU 显存

8.1 四阶段实施计划

阶段目标周期关键交付物
Phase 1
基础架构		 后端服务层 + 数据库 + 认证 2 周 Node.js API、PostgreSQL、JWT 认证、项目 CRUD、localStorage 升级
Phase 2
ComfyUI 打通		 模型接入层 + 实时通信 2 周 ComfyUI Proxy、WebSocket 进度推送、图片/视频/音频生成端到端
Phase 3
智能体系统		 原生 Agent + 自然语言驱动 2 周 LangGraph Agent、意图识别、自动工作流构建、多模型调度
Phase 4
生产优化		 性能 + 稳定性 + 生态 2 周 虚拟渲染、任务队列、监控告警、社区分享、模板市场

8.2 Phase 1 详细任务拆分

Week 1：后端骨架 + 数据库

  • Day 1-2：初始化 Node.js Express 项目，配置 TypeScript、ESLint、Prettier
  • Day 3：PostgreSQL + Prisma Schema 设计（User/Project/Workflow/Asset 表）
  • Day 4：JWT 认证（注册/登录/刷新 Token）
  • Day 5：Project CRUD API + 画布状态序列化/反序列化

Week 2：前端对接 + 持久化

  • Day 1-2：axios 封装 + React Query 集成 + 错误处理
  • Day 3：前端登录/注册 UI + 路由守卫
  • Day 4：画布自动保存（防抖 5s）+ 项目列表页
  • Day 5：localStorage 迁移到 API + 离线缓存策略

8.3 Phase 2 详细任务拆分

Week 3：ComfyUI 接入

  • Day 1-2：Python FastAPI 项目搭建 + ComfyUI Client 封装
  • Day 3：图片生成链路打通（文本节点 → ComfyUI Flux → 结果回传）
  • Day 4：视频/音频生成链路打通
  • Day 5：多模型路由（根据参数自动选择 ComfyUI 工作流模板）

Week 4：实时通信

  • Day 1-2：Socket.io 服务端 + 客户端集成
  • Day 3：ComfyUI WebSocket 代理（进度实时推送）
  • Day 4：节点状态实时更新（生成中/完成/失败）
  • Day 5：文件上传（Multer + MinIO）+ 生成结果下载

8.4 Phase 3 详细任务拆分

Week 5-6：智能体系统

  • LangGraph 工作流定义（意图识别 → 任务拆解 → 工作流规划 → 执行）
  • 画布上下文感知（读取当前画布节点 → 作为 Agent 上下文）
  • 自然语言 → 节点拓扑自动转换
  • 工具调用（每个节点类型注册为 LangChain Tool）
  • Agent 对话 UI（右下角浮动面板，对标 RHTV）

8.5 风险与应对

风险概率影响应对策略
ComfyUI 部署复杂高高使用 ComfyUI 云服务（RunningHub）作为过渡方案
GPU 资源不足高高按需调用云 API（LiblibAI / RunningHub API）
React Flow 性能瓶颈中中Phase 4 虚拟渲染优化，渐进式改进
Agent 幻觉问题中中严格 Function Calling + 人工确认关键操作
多模型兼容性中中抽象模型接口层，模型切换不影响上层逻辑
