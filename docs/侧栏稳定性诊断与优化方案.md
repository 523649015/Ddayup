# Ddayup 侧栏（extension/）视频卡稳定性与性能 —— 代码级诊断与优化方案

> 适用版本：2026-09-05（含五轮修复）。文末附验证方法与可直接使用的诊断工具。

## 1. 数据流与「卡数忽多忽少 / 封面时有时无」的根因

### 1.1 完整数据流

```
┌─ 源页（douyin.com）────────────────────────────────────────────┐
│ inject-main.js（MAIN 世界）                                      │
│   fetch/XHR 钩子 → __hmdao_captures（按 awemeId 索引：           │
│   dyCoverByAweme / dyTitlesByAweme / dyEpisodeByAweme /          │
│   dyVideoUrlByAweme / dyMixIdsByAweme）                          │
│   + hmdaoTryFetchMixAweme（合集列表分页拉取，≤10页）              │
│   + hmdaoPersistCaps（sessionStorage，2h TTL）                   │
└──────────────┬───────────────────────────────────────────────────┘
               ▼
┌─ background（SW）scan.js scanTab ──────────────────────────────┐
│ 触发源：10s 轮询 / 手动扫描 / SPA pushState(节流5s) / 切集事件    │
│ 串行保护：HMDAO_SCAN_RUNNING（上一轮未完成则丢弃）                │
│ 合并：MAIN捕获 + 网络层 + DOM解析 + 深度解析 → dedupMap           │
│   → 同 awemeId 折叠（aidScore: dashAudio4+cover2+episode1）      │
│   → 野卡过滤 / mixId 成员过滤 / 图片上限 60                      │
│ 广播签名跳过：HMDAO_LAST_BCAST_SIG（无变化不发 SCAN_RESULT）      │
└──────────────┬───────────────────────────────────────────────────┘
               ▼
┌─ 侧栏 sidepanel.js SCAN_RESULT 处理器 ─────────────────────────┐
│ mixId 变化 → 清空（批量+普通抖音卡）                              │
│ 分流：视频→batchAssets（批量容器）/ 其余→window.assets           │
│ 合并：awemeId 优先 → ①同id同url补元数据 ②同id异url原地换url       │
│       ③同url补元数据 ④新增追加（增量合并，从不删除）              │
│ lastScan 持久化（签名+3s节流）                                   │
└──────────────┬───────────────────────────────────────────────────┘
               ▼
┌─ card-render.js renderNow ─────────────────────────────────────┐
│ 150ms 去抖 → 排序 → 内容签名（stableKey+cover+title+notPlayed）  │
│ 签名未变 → 直接 return（零 DOM 操作）                             │
│ 键控复用：data-stable-key 匹配 → 新建/patchCard/移除              │
│ 封面：coverWhenVisible（IntersectionObserver 600px 预取          │
│       + 去签名缓存 HMDAO_COVER_CACHE + 4 路并发限流）             │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 已定位并修复的根因（按用户症状对应）

| 症状 | 根因 | 修复位置 |
|---|---|---|
| 卡数忽多忽少 | `dyVideoUrlByAweme` 被推荐流/feed 污染，episodeMap（数组下标派生、随 chunk 变化）当成员名单 | scan.js：`dyMixIdsByAweme` 归属过滤（空归属时不过滤防误杀） |
| 卡数骤降再回升（闪烁） | SPA 切集整体 `delete __hmdao_captures`，封面/标题/集数索引清零 | inject-main.js：`hmdaoResetCaptures` 同页切集（pathname 相同）只清瞬时数组、保留索引 |
| 切合集封面新旧跳动 | 同 pathname 只变 modal_id → 旧合集索引残留；sessionStorage 恢复跨合集数据 | inject-main takeMix 检测 mixId 变化清索引；scan.js `HMDAO_TAB_MIXID`；持久化盒记 mixId |
| 封面/标题每 10s 翻转 | 同集双卡（实时流卡 vs API 合成卡，url 不同躲过 url 去重）→ applyMeta 按数组顺序交替吸收 | scan.js 广播前按 awemeId 折叠（aidScore 高者赢），输入顺序反转测试保证稳定 |
| 封面时有时无 | 封面为限时签名 URL，每轮扫描签名变化被判定"封面变了"→ 103 张卡每轮重拉 | card-render.js：`coverCacheKey`=origin+pathname 去重 + IO 懒加载 + 4 路限流 |
| 集数与标题矛盾 | 集数=cursor+数组下标（cursor 是分页游标） | 集数权威序：desc「第N集」解析 > mix_info.current_episode > 下标（只填补不覆盖）；渲染层 `titleEpisodeNo` 自愈 |
| 双「第N集」字样 | episodeNo 与标题内「第40集」并排 | stripEpisodePrefix（行首）+ displayName 标题自带集数时不加前缀 |

### 1.3 用户期望行为的实现："源页没操作，卡就不增不减不换"

- **不增**：SCAN_RESULT 广播签名 + 侧栏合并只追加真实新 awemeId/url；
- **不减**：增量合并从不删除；换页清空只按 URL/合集身份判定；
- **不换**：同集折叠保证单一元数据来源；封面缓存按去签名 key（签名轮换不触发重载）；patchCard 仅在缓存 key 变化时才换图。

### 1.4 残余风险（未修，按优先级）

1. **多标签广播串扰**：SCAN_RESULT 广播不按 `msg.tabId` 过滤，两个抖音标签会互相合并资产。建议：侧栏只接受 `tabId === window.__hmdao_sourceTabId` 的广播（或按 tab 分容器）。
2. **`HMDAO_COVER_CACHE` 的 blob URL 永不 revoke**：133 张封面 × 数百 KB，长期挂机会累积。建议改 LRU（上限 ~200）并在淘汰时 `URL.revokeObjectURL`。
3. **`renderNow` 的 `window.assets.indexOf(a)` 是 O(N²)**：200 张卡约 4 万次比较，千卡级会卡。建议先建 `Map<asset,index>`。
4. **无虚拟列表**：卡数 >300 时 DOM 节点数（含封面 img）会拖慢滚动。建议窗口化渲染（可视区 ±缓冲屏）。

## 2. 「关闭视频卡后仍有声音」排查

### 2.1 已堵死的路径

| 泄漏路径 | 状态 |
|---|---|
| 主预览 `previewVideo` / `previewAudio` 未 pause | closePreview 已 `pause+removeAttribute+load()` |
| 悬停抽帧单例 `hoverVideoEl` 未销毁 | closePreview + **renderNow 移除卡片时**（本次新增：`el.contains(hoverVideoEl)` 检查）双重销毁 |
| 悬停试听（audio 卡 onmouseenter）mouseleave 不触发（卡片被移除） | 本次新增：移除卡片前 `stopHoverAudio()` |
| DASH 合并 blob、动态创建的 video/audio | closePreview 兜底 `document.querySelectorAll('video,audio')` 全量 pause |
| 源页音频（HMDAO_PLAY_PAGE_AUDIO） | `HMDAO_STOP_PAGE_AUDIO` / stopHoverAudio 发停止消息 |

### 2.2 仍可能的残留点（用 §4 工具可实测）

1. **卡片在 hover 中被 patchCard 复用**：节点未移除，mouseleave 正常触发，无泄漏（已排除）。
2. **`previewAudio` 与 `previewVideo` 之外的第三方媒体**：如 yt-dlp 起的画中画、`document.pictureInPictureElement` —— 建议在 closePreview 加 `exitPictureInPicture()`。
3. **源页自身的播放**：侧栏关闭后源页视频继续出声是**正常行为**（那是源页自己的播放器）；若要"侧栏关闭即静音源页"，需要显式产品决策 + `HMDAO_STOP_PAGE_AUDIO` 全量调用。

## 3. 性能瓶颈与内存泄漏风险清单

| # | 风险点 | 现状 | 建议 |
|---|---|---|---|
| 1 | SPA pushState 重扫风暴（**抖音专属卡顿真根因**） | 已修：MIN_GAP 5s + 扫描中丢弃 + auto 轻量路径 | 保持；必要时提到 8s |
| 2 | 200 个封面 relay 并发打满 SW | 已修：IO 懒加载 + 4 路队列 + 去签名缓存 | 队列加优先级（可视区优先） |
| 3 | 自动抽帧拉视频字节（原 8MB/张） | 已修：仅视口内 + 全局预算 6 + 2MB | 预算耗尽后提示用户手动 hover |
| 4 | **`HMDAO_COVER_CACHE` blob 永不释放** | 未修 | LRU + revoke（见 §5.2） |
| 5 | 每次 SCAN_RESULT 全量 `JSON.stringify` meta 比较 | 已限 META_KEYS 8 个字段 | 大合集（>300）可改为 hash 缓存 |
| 6 | `window.assets.indexOf` O(N²) | 未修 | Map 索引（§5.3） |
| 7 | `NETWORK_ASSETS[tabId]`（SW 全局）同页累积 | 有换页清空 + 图片上限 60 | 观测 `__hmdaoHealth` 的资产数趋势即可 |
| 8 | 定时器：`POLL_TIMERS`（每 tab 10s）、`RESCAN_TIMERS`、`hmdaoPendingRescan`、`__renderTimer` | poll/scan 有 stop 路径；**tab 关闭时是否 stopPolling 未确认** | 确认 `chrome.tabs.onRemoved` 里调 `stopPolling(id)` |
| 9 | 事件绑定：卡片每次 renderNow 新建时绑定 onclick 等 | 旧卡随 DOM 移除被 GC，键控复用后不重复绑定 | 无需处理；避免在 document 级重复 addEventListener |
| 10 | 闭包持有：卡片闭包引用资产 a（含 dyFormats 大数组） | 卡片存在即持有，属预期 | 虚拟列表落地后自动缓解 |
| 11 | `logOnChange`/`imgDimensions` Map 无上限 | 键/尺寸有限 | 加容量上限（如 5000）保险 |
| 12 | base64 消息中转（2MB→2.7MB 字符串） | 已限频限流 | 大文件下载改走 D2 通道（已知方案） |

## 4. 测试定位问题的代码方案（已落地，侧栏控制台直接用）

### 4.1 一键健康报告

侧栏右键 → 检查 → Console：
```js
window.__hmdaoHealth()
```
输出：资产/批量容器数量、DOM 内媒体元素（含**正在播放**的清单及 src 前 80 字符）、**游离媒体元素数**、封面缓存/队列/并发、DOM 卡片数、堆内存 MB。**间隔 5 分钟跑两次对比 `heapMB` 与 `mediaInDom`，即可判断是否泄漏。**

### 4.2 媒体泄漏监视器（定位"关卡后仍有声音"）
```js
window.__hmdaoWatchMedia(true)   // 开启
// …滚动、点卡片、关卡片…
window.__hmdaoWatchMedia(false)  // 关闭
```
捕获阶段拦截 `play` 事件 + MutationObserver 监视媒体元素挂载/卸载。**关键告警**：`⚠ 移除了仍在播放的媒体元素（这就是声音残留）` —— 出现即锁定了泄漏点（元素、src）。

### 4.3 SW 侧观测（background Service Worker 控制台）
- `[HMDAO][scan] 上一轮扫描未结束，跳过本轮` —— 风暴治理生效标志；
- `[HMDAO][scan] 同集多来源折叠：N → M 条` —— 交替引擎修复生效标志；
- `[HMDAO][bg] FETCH_MEDIA` 频率 —— 封面风暴是否复发（应只在新封面首次进入视口时出现）。

### 4.4 回归测试
```powershell
node scripts/test-douyin-episode-index.mjs   # 84 断言：集数/折叠/治理/风暴/同步全链路
node scripts/test-douyin-collection-dedup.mjs
node scripts/test-douyin-collection-clickable.mjs
```

## 5. 优化建议（按投入产出排序）

### 5.1 已落地（本会话）
去签名封面缓存 + IO 懒加载 + 4 路限流；同集折叠；广播签名跳过；扫描串行化 + SPA 重扫风暴治理；lastScan 节流；图片上限 60；切合集双端清空；媒体元素移除时停声；扩展重载清 lastScan。

### 5.2 封面缓存 LRU（~15 行）
```js
// card-render.js coverFetch 命中写缓存处替换：
if (b) {
  if (HMDAO_COVER_CACHE.size >= 200) {
    const oldest = HMDAO_COVER_CACHE.keys().next().value;
    const old = HMDAO_COVER_CACHE.get(oldest);
    if (old && old.startsWith('blob:')) { try { URL.revokeObjectURL(old); } catch (_) {} }
    HMDAO_COVER_CACHE.delete(oldest);
  }
  HMDAO_COVER_CACHE.set(key, b); // Map 迭代序=插入序，天然 LRU
}
```

### 5.3 renderNow 去 O(N²)
```js
// filtered.forEach 里 const gi = window.assets.indexOf(a); 替换为循环前：
const idxMap = new Map(window.assets.map((x, i) => [x, i]));
// 循环内：const gi = idxMap.get(a);
```

### 5.4 广播按 tabId 过滤（多标签隔离）
侧栏 SCAN_RESULT 处理器开头：
```js
if (msg.tabId != null && window.__hmdao_sourceTabId != null && msg.tabId !== window.__hmdao_sourceTabId) return;
```

### 5.5 虚拟列表（卡数 >300 时再做）
`#list` 用 `content-visibility: auto` + `contain-intrinsic-size` 一行 CSS 即可获得 80% 收益，无需完整虚拟滚动：
```css
#list .card { content-visibility: auto; contain-intrinsic-size: 180px; }
```

### 5.6 媒体生命周期统一管理（防御性）
全局 MediaRegistry：所有动态创建的 video/audio 注册进 `Set<WeakRef>`，`stopAllMedia()` 遍历 pause+清 src；在 closePreview、侧栏 `beforeunload`、卡片批量移除时统一调用（当前是三处各自为战，注册表可消灭"漏网"类 bug）。
